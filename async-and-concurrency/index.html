Event Loop

JS is single threaded, that means only one task can be executed at a time. But we all know that JS can handle asynchronous operations.
How does it manage to do that? With the help of the event loop.

Where is event loop located?

Event loop is not part of the JS engine, but a mechanism provided by the runtime (like browsers or Node.js) that runs the JS code. The architecture is:

  • JS engine (V8, SpiderMonkey, etc.)
  • Event loop (provided by the runtime)
  • Web APIs (setTimeout, fetch, etc.)
  • Call stack (synchronous operations)
  • Task queues (asynchronous callbacks)

How it works?

  1. JS engine executes synchronous code
  2. Asynchronous operations are delegated to Web APIs
  3. When an asynchronous operation completes, its callback is placed in a task queue
  4. The event loop checks the call stack and task queues, moving callbacks to the call stack when it's empty

What's the priority and why?

  1. Synchronous code (call stack) — highest priority, runs immediately.
  2. Microtasks (Promise callbacks, MutationObserver) — run after the current synchronous code, before any rendering or I/O. Microtasks are given higher priority than macrotasks to ensure data consistency, which is why we run all microtasks before any macrotask.
  3. Rendering — happens after microtasks, before macrotasks. This lets the browser update the UI before handling any new user interactions or I/O.
  4. Macrotasks (setTimeout, setInterval, I/O callbacks) — run after microtasks and rendering. Macrotasks can be long and heavy; if we ran them all at once we could freeze the UI. This is why we run only one per loop, to ensure the re-render.

Microtask starvation

The eventloop must be fully drained before rendering or moving to the next macrotask. If this never happens, it can lead to performance issues and a frozen UI.

Promises

Is an object that manages the asynchronous operations (it can be failure or completion). It’s like a contract that promise us to provide the result in the future. Also it provides different states like pending, fulfilled or rejected.

Patterns

Promise.all

Waits for all promises to be fulfilled, or for any to be rejected. It’s useful when you need to perform multiple asynchronous operations in parallel and wait for all of them to complete before proceeding.

Promise.race

Waits for the first promise to be fulfilled or rejected. It’s useful when you want to perform multiple asynchronous operations in parallel and proceed as soon as one of them completes, regardless of the outcome.

Promise.allSettled

Waits for all promises to be settled (either fulfilled or rejected). It’s useful when you want to perform multiple asynchronous operations in parallel and wait for all of them to complete, regardless of the outcome.

Promise.any

Waits for the first promise to be fulfilled. It’s useful when you want to perform multiple asynchronous operations in parallel and proceed as soon as one of them completes successfully.

await/async

Syntactic sugar over promises that allows you to write asynchronous code in a more synchronous and readable manner. It’s useful for improving code readability and maintainability when working with complex asynchronous operations.


Why the console.log(user) is not executed until we don't fetch the user?
Because that's exactly what await is for: it pauses the async function at that point and only resumes it once the promise settles.

Web workers

Web Workers are a way to run JavaScript in background threads, allowing for concurrent execution of code without blocking the main thread. They are useful for performing heavy computations or handling tasks that would otherwise cause the UI to become unresponsive.

  • True multithreading — Web Workers enable parallel execution on multiple CPU cores.
  • Isolated scope — workers run in a different global context (self) and do not have access to the DOM, the window object, or the document object.
  • Message passing — communication between the main thread and the worker occurs via the postMessage() method and onmessage event handler.

Type of workers

  • Dedicated Workers — the most common type, used for a single task or module.
  • Shared Workers — can be accessed by multiple scripts, even across different windows or iframes.
  • Service Workers — a special type of worker that acts as a proxy between the web application and the network, enabling features like offline support, background sync, and push notifications.

Use cases

  • Heavy computations (e.g., data processing, image manipulation, etc.)
  • Background tasks (e.g., handling WebSocket connections, performing periodic updates, etc.)

Basic example

Two files: the page that starts the worker, and the worker script itself. They talk to each other with postMessage / onmessage.

While the worker is computing fib(40) (~1s), the page stays interactive — you can type, scroll, click. That's the whole point. Communication is one-way per postMessage: values are copied (structured clone), not shared. For large buffers, pass them as transferable objects: worker.postMessage(buffer, [buffer]) moves ownership instead of copying.
